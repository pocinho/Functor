# ADR-0016: Evidence file layout, request lock and repair

## Status

Accepted

## Context

[ADR-0013](ADR-0013-run-lifecycle-and-evidence-persistence.md) and [ADR-0015](ADR-0015-validation-report-persistence-and-events.md) fix the lifecycle and the publication order of evidence, and name `content/evidence/captures/<hex>` and `content/evidence/reports/<artifact-id>.json`. Implementing P1.2 exposed details they leave open or state in a way the store cannot follow:

- An artifact's id is generated by the store inside `create`, so a file named by it cannot be written before the artifact exists.
- Inline content is capped at 1 MiB, while captured streams may reach 8 MiB each and results reference them.
- "Idempotent by request id" needs a check-and-create that no two processes can interleave, but the write lock covers one entity write, not two.
- A failure after the commit point leaves relationships missing.

## Decision

1. **Content-addressed evidence files.** Every evidence file lives at `content/evidence/<area>/<sha256 hex>`, with areas `captures`, `streams`, `outputs`, `results` and `reports`. Names come from the bytes, so a file can be written before its artifact, shared by identical bytes, verified by re-hashing, and repaired when found damaged. This supersedes the `<artifact-id>.json` name for reports in ADR-0015.
2. **Run intent is inline JSON; larger records are files.** The `run` artifact keeps its intent as inline JSON (small and bounded). The `run_result` artifact references a JSON document in `results/`, which holds the exit status, truncation, diagnostics, output references and the digests and sizes of the two streams. Streams are stored in `streams/`, so no record approaches the inline limit.
3. **Outputs are ordinary artifacts.** Output artifacts carry the declared type and format, content in `outputs/`, and the non-reserved metadata `run`, `output` and `sha256`. They are not evidence artifacts and remain editable; the `run_result` and the `derived_from` edge record what the run produced.
4. **Capture consistency.** A capture reads the artifact and its bytes, then reads both again; if the revision or the bytes differ, it retries once and then fails with `Conflict`. A capture exists only for a state that was observed twice.
5. **Request lock.** Recording an intent first takes `.functor/runs/request-<request-id>.lock` (waiting up to the lock timeout), then checks for an existing run with that request id and creates the run. Two concurrent recordings of one request therefore produce one run; the other caller receives the existing run with `created = false`.
6. **Run lease.** `.functor/runs/<run-id>.lock` is an exclusive file lock held for the lifetime of the owner. Dropping it, or the owner dying, releases it. A run without a result is `running` while the lease is held and `interrupted_unknown` otherwise. `.functor/runs/` is not repository state and is not versioned; projects that commit repositories should git-ignore it.
7. **Relationship repair.** The edges of ADR-0014 are derived from the records (`capture.source`, the intent's capture ids, `run_result.run` and `outputs`, `validation_report.subject`). `recover` creates any that are missing, and a repeated `record_intent` repairs the run it returns. Creating an edge that already exists is not an error.
8. **Failures after the commit point.** Once the `run_result` exists the run is complete. If a relationship write then fails, the call still returns the error (a failed mandatory write is never reported as success), the run reads as complete, and `recover` repairs the edges.
9. **Reports.** The stored report document is the JSON of `functor validate --output json` (schema version 1, sorted keys, no timestamp); the validation time and the subject (artifact id, revision, content digest) are artifact metadata. `validates` is created for an artifact subject only.
10. **Dependencies.** `functor-store` gains `sha2` (digests) and `serde_json` (documents), as the crate that owns the representation ([ADR-0005](ADR-0005-serialization-boundary.md)). Neither enters `functor-model` or `functor-core`.

## Consequences

- Evidence survives restarts and moves, is checkable by re-hashing, and a damaged or missing file is reported as `Inconsistent` with the path.
- The loader already reports a missing content file for any artifact, so a repository with a deleted evidence file is refused for ordinary reads until it is restored; this is existing behavior and a deliberate safety property.
- Content-addressing means two captures of identical bytes share one file; separate `capture` artifacts still record each observation.
- Orphan files (written before an artifact that failed) are harmless and are reported later by validation (`V0022`, P1.4); nothing deletes them.

## RFC Impact

None beyond ADR-0013 and ADR-0015.
