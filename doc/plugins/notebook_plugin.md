# NOTEBOOK PLUGIN (Draft)

## 1. Purpose
The Notebook Plugin provides a **reactive, cell‑based execution environment** for Functor, enabling users to write narrative documents containing executable F# code that manipulates the Functor editor state. Notebook mode operates **simultaneously** with editor mode, sharing the same MVU core and dispatch loop.

The plugin is designed to be:
- **headless** (no Avalonia dependency)
- **portable** (CLI, WASM, agentic workflows)
- **deterministic** (pure MVU semantics)
- **HTML‑rendered** (primary output format)

---

## 2. Architectural Goals

### 2.1 MVU Purity
Notebook mode must preserve Functor’s MVU guarantees:
- Single immutable `Model`
- Pure `update` function
- Deterministic state transitions
- No hidden state

Cells dispatch **Messages** into the MVU loop.  
Notebook outputs are pure projections of the model.

### 2.2 Multi‑Mode Operation
Notebook mode runs **alongside** editor mode:
- Both drivers dispatch messages
- Both drivers subscribe to model changes
- Both views render independently
- Both operate on the same shared model

This enables:
- live documentation  
- teaching mode  
- agentic workflows  
- reactive editor introspection  

### 2.3 Plugin Isolation
Notebook functionality is implemented as a plugin:
- optional  
- sandboxed  
- self‑contained  
- extensible  

It does not modify Functor.Core or Functor.App.

## 3. Notebook Plugin Responsibilities

### 3.1 Load Notebook Files
- Parse Markdown + code blocks  
- Support `.functornb` with cell annotations  
- Build a list of cells with stable IDs  

### 3.2 Build Dependency Graph
- Track cell dependencies  
- Compute topological order  
- Mark cells dirty when dependencies change  
- Recompute cells reactively  

### 3.3 Execute Cells
- Run cell code inside a controlled execution context  
- Dispatch messages generated by cells  
- Capture outputs (text, HTML, images)  

### 3.4 Render Outputs
- Convert cell results into HTML  
- Embed Skia surfaces as images  
- Provide a unified HTML document for notebook view  

### 3.5 Expose Commands
- Run a single cell  
- Run all cells  
- Export notebook  
- Refresh notebook  
- Show notebook panel in Functor.App

## 4. Rendering Strategy

### 4.1 Architectural Decision
**HTML is the primary rendering target for notebook outputs.**

Reasons:
- portable  
- works in Avalonia WebView  
- works in WASM  
- works in CLI (HTML export)  
- supports rich layout  
- supports interactive widgets  
- avoids building a Skia widget framework  

### 4.2 Skia Rendering
Skia is used **headlessly**:
- render to `SKSurface`  
- convert to `SKImage`  
- encode to PNG or SVG  
- embed as `<img src="data:image/png;base64,...">`  

This preserves Functor’s Skia rendering capabilities without requiring a widget system.

### 4.3 HTML Rendering Pipeline

```
CellOutput
    ↓
RenderOutput (Text | Html | SkiaImage | Svg)
    ↓
HtmlRenderer
    ↓
NotebookView (HTML document)
    ↓
Frontend (Avalonia WebView, WASM, CLI export)
```

#### Pipeline Steps

1. **Cell Execution**
   - Cell code runs and produces a `CellOutput`.

2. **Output Normalization**
   - Convert raw output into a `RenderOutput` discriminated union:
     - `RenderOutput.Text`
     - `RenderOutput.Html`
     - `RenderOutput.SkiaImage`
     - `RenderOutput.Svg`

3. **Skia → HTML Conversion**
   - Encode Skia surface to PNG bytes.
   - Base64 encode.
   - Wrap in `<img>` tag.

4. **HTML Assembly**
   - Combine cell outputs into a structured HTML document.
   - Include metadata, cell ordering, and styling.

5. **Frontend Display**
   - Avalonia WebView (editor mode)
   - WASM (browser mode)
   - CLI (HTML export)

## 6. Interaction with Functor.Core

### 6.1 Message Dispatch
Cells mutate the editor state by dispatching messages:

```
context.Dispatch(Message.InsertText "hello")
```

### 6.2 Model Subscription
NotebookDriver subscribes to model changes:

```
context.Subscribe(fun model -> ...)
```

### 6.3 Deterministic Execution
All state changes flow through the MVU update loop.

---

## 7. Interaction with Functor.App

### 7.1 Notebook Panel
Functor.App may host a notebook panel:
- displays HTML output  
- allows running cells  
- shows execution logs  

### 7.2 Editor ↔ Notebook Synchronization
Editor actions may:
- mark cells dirty  
- trigger recomputation  
- update notebook outputs  

Notebook actions may:
- insert text  
- move cursor  
- apply selections  
- run commands  

Both modes remain consistent through MVU.

## 10. Interactive Plotting and Data Analysis

Functor.Notebook supports embedding interactive HTML visualizations using established JavaScript libraries such as:

- Plotly.js  
- Vega / Vega-Lite  
- D3.js  
- ECharts  
- Chart.js  

These libraries enable:
- zooming  
- panning  
- brushing  
- point selection  
- linked views  
- reactive filtering  

### Reactive Event Pipeline

1. A cell renders HTML containing a visualization.
2. The visualization emits events (e.g., selection).
3. A JavaScript bridge sends event data to the Notebook Plugin.
4. The plugin dispatches a `NotebookEvent` message.
5. The MVU update loop updates the model.
6. Dependent cells re-run.
7. NotebookView re-renders updated HTML.

This architecture mirrors Marimo’s reactive notebook model and integrates seamlessly with Functor’s MVU core.

---

## 11. Summary

The Notebook Plugin provides a **reactive, HTML‑rendered, MVU‑driven** execution environment that integrates seamlessly with Functor’s editor mode. By using HTML as the primary rendering target and Skia only for headless image generation, the plugin remains portable, safe, and easy to extend.

This architecture enables:
- simultaneous editor + notebook operation  
- deterministic reactive execution  
- multi‑frontend support  
- future agentic workflows
